# Викладка для баєрів: інструкція простою мовою

Це інструкція для тебе, не для програміста. Тут: що вписати у Vercel, як створити бота в Telegram, як уберегти Supabase від «засинання» і єдиний чеклист по порядку (розділ 7).

**Стан на 2026-10-18 (крок 3.1 пакета 3):** готова лише частина про Vercel і підготовку збірки. Розділи про Supabase (таблиці, функція входу) допишу на кроці 3.2, чеклист у розділі 7 уже повний, але деякі пункти чекають на мої кроки (позначено).

Нічого не публікується само: ні акаунтів, ні сайту я не створював.

## 1. Що саме вписати у Vercel

> **Робити лише перед самим запуском тесту** (див. чеклист, розділ 7). Є один виняток: перевірити вхід через Telegram можна лише на справжній адресі сайту, тому один пробний деплой знадобиться трохи раніше. Посилання тоді нікому не розсилай.

Коли у Vercel натискаєш «Add New → Project» і вибираєш репозиторій, у формі «Configure Project» вписуєш:

| Поле у Vercel | Що вписати |
|---|---|
| **Framework Preset** | `Other` |
| **Root Directory** | `app-mvp` (натисни Edit і вибери папку; без цього збірка не знайде застосунок) |
| **Build Command** | `npx expo export --platform web` (вмикай перемикач Override і впиши) |
| **Output Directory** | `dist` (теж Override) |
| **Install Command** | залиш типовий (`npm install`) |
| **Node.js Version** (Settings → General) | `22.x` |

Решту (редирект усіх адрес на головну сторінку, заборону індексації, кешування) уже зроблено у файлі `app-mvp/vercel.json`, нічого вписувати не треба.

Тариф: **Hobby** (безкоштовно). На Hobby діє умова Vercel про особисте некомерційне використання; ти це знаєш і переходиш на Pro з релізом.

Яка гілка деплоїться: у Vercel → Settings → Git → **Production Branch** впиши `grindyk-real-renders` (тоді не треба зливати в `main`). Гілку `main` зливаєш лише ти.

Назву проєкту у Vercel дай нейтральну й не очевидну (не «grindset-test»): від неї залежить адреса `назва.vercel.app`.

## 2. Змінні середовища (Environment Variables) у Vercel

У Vercel: Settings → Environment Variables. Додаєш чотири змінні (усі для Production):

| Змінна | Що вписати | Де взяти |
|---|---|---|
| `EXPO_PUBLIC_SUPABASE_URL` | адреса проєкту, виглядає як `https://xxxx.supabase.co` | Supabase → Project Settings → API → Project URL |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | довгий ключ `anon public` | Supabase → Project Settings → API → `anon` `public` |
| `EXPO_PUBLIC_TELEGRAM_BOT` | імʼя бота без `@`, наприклад `my_test_bot` | з кроку 3 цієї інструкції |
| `EXPO_PUBLIC_INCLUDE_RESTRICTED` | **`false`** | див. нижче |

> **Про `EXPO_PUBLIC_INCLUDE_RESTRICTED`.** У відповіді ти написав «`true`, поки ризикові модулі не переписані», а далі, що бандл Vercel публічний і «як робити»-контент у нього потрапляти не має. Ці дві вимоги суперечать одна одній: при `true` повні ризикові тексти лежать у файлі, який віддається кожному, хто знає адресу. Тому у цій інструкції й у налаштуваннях збірки стоїть **`false`** (публічний набір без ризикових фрагментів). **Підтверди або виправ.** Якщо вирішиш `true`, це змінюється однією змінною у Vercel, але ризик тоді твій.

**Важливо про секрети.**
- Ключ `anon public` публічний за задумом: доступ до даних обмежують правила в Supabase, а не секретність ключа.
- **Ніколи не вписуй у Vercel** ключ `service_role` і токен бота. Токен бота й `service_role` живуть лише в Supabase (розділ 4), без них тестовий вхід у Vercel не працює, і це правильно.
- Поки Supabase не підключено (крок 3.2), застосунок збирається й працює як раніше, без входу.

## 3. Бот у Telegram (@BotFather), покроково

Бот потрібен лише для кнопки «Увійти через Telegram». Писати від його імені він нічого не буде.

1. У Telegram відкрий чат із **@BotFather** (синя галочка, офіційний).
2. Напиши `/newbot`.
3. Він спитає **імʼя бота** (те, що бачать люди, наприклад «Тест курсу»). Не вживай «Facebook», «Meta» тощо.
4. Далі **username бота**: латиниця, обовʼязково закінчується на `bot`, наприклад `kurs_test_bot`. Запиши його без `@`: це і є значення для `EXPO_PUBLIC_TELEGRAM_BOT`.
5. BotFather пришле **токен** (довгий рядок на кшталт `123456:ABC-...`). Це пароль бота. Нікому його не показуй, не пиши в чат і не вставляй у Vercel. Його ти вставиш лише в Supabase (розділ 4).
6. Привʼязка сайту до бота: надішли BotFather `/setdomain`, вибери свого бота й впиши адресу сайту **без `https://`**, наприклад `назва.vercel.app`. Це роблять **після першого деплою на Vercel**, коли адреса відома. Доки адреса не привʼязана, кнопка входу не працюватиме.
7. Якщо потрібен інший домен пізніше, `/setdomain` можна повторити.

Примітка: у Telegram цей спосіб входу називається «Login Widget» і в офіційній документації лежить на сторінці з назвою «legacy» (застарілий). Він працює, але Telegram розвиває й новий спосіб входу (через `oauth.telegram.org`). Назви кроків у BotFather можуть трохи відрізнятись від написаного вище. Якщо щось не збігається, надішли мені скріншот, ми розберемось разом на кроці 3.2.

Тестерам потрібно мати у Telegram **@username** (Налаштування → Імʼя користувача). Без нього зайти не вийде.

## 4. Supabase (безкоштовний план)

Допишу на кроці 3.2: SQL для таблиць `allowed_users`, `progress`, `feedback`, `events`, `keepalive` одним файлом, який вставляєш у Supabase (SQL Editor), і функція входу `telegram-auth`, у якій зберігається токен бота.

Що відомо вже зараз:
- Проєкт, який «заснув», розморожується в панелі Supabase кнопкою **Restore project** (відновлення займає кілька хвилин).
- На Free проєкт засинає після тижня без активності. Тому зроблено keep-alive (розділ 5).
- У Supabase секрети функції вписують у Edge Functions → Secrets: `TELEGRAM_BOT_TOKEN` і ключ `service_role` (Supabase сам підставляє `service_role` у функції, тому окремо його найчастіше вписувати не треба; уточню на кроці 3.2).

## 5. Keep-alive: щоб безкоштовний Supabase не засинав

Що це: заготовка `ci/supabase-keepalive.yml` (після увімкнення вона працює як `.github/workflows/supabase-keepalive.yml`) кожні 3 дні надсилає в Supabase крихітний запит (читання одного рядка таблиці `keepalive`). Для Supabase це звичайна активність, тож «лічильник тижня» скидається.

Що зробити тобі:
1. **Увімкнути файл.** Мій git не має права створювати файли в `.github/workflows` (GitHub відхилив це), тому заготовка лежить у `ci/`. На сайті GitHub: репозиторій → Add file → Create new file → у назві впиши `.github/workflows/supabase-keepalive.yml` → встав увесь вміст файла `ci/supabase-keepalive.yml` → Commit changes → вибери гілку **main**. Так файл одразу опиниться там, де за розкладом його запускає GitHub.
2. GitHub → репозиторій → Settings → Secrets and variables → Actions → New repository secret.
3. Додай два секрети: `SUPABASE_URL` (та сама адреса `https://xxxx.supabase.co`) і `SUPABASE_ANON_KEY` (ключ `anon public`).
4. Вкладка Actions → «Supabase keep-alive» → Run workflow: перевір, що запуск зелений.

**Відомі ризики (їх треба знати):**
1. **Умови Supabase.** Я не знайшов в офіційних умовах або документації Supabase ні дозволу, ні заборони на такі запити; сторінка тарифів лише каже, що Free-проєкти засинають після тижня неактивності й не визначає, що саме вважати активністю. Спільнота широко користується цим прийомом, але **офіційного підтвердження в мене нема**. Якщо Supabase колись це заборонить, повернемось до Pro.
2. **За розкладом файл запускається лише з головної гілки `main`.** Тому в пункті 1 вище файл створюється одразу в `main`. Поки його там нема, розклад не працює, і засинання треба стерегти руками (раз на кілька днів заходити в панель Supabase).
3. **Ненадійність розкладу.** GitHub інколи затримує або пропускає заплановані запуски. Якщо запит не пройде, GitHub надішле лист про помилку запуску: тоді відкрий Supabase і натисни Restore.
4. **Не рятує від паузи, що вже настала.** Запит лише запобігає засинанню; якщо проєкт заснув, його треба розбудити вручну.
5. Якщо буде ненадійно, повертаємось до Pro ($25 на місяць).
