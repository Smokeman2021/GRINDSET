# Пакет 2: плани блоків Б, Е, В, Г, Д (на погодження)

Статус на 2026-10-12: блок А виконано (див. нижче й `docs/DECISIONS.md`). Для блоків Б–Е, за твоїм правилом, спершу план, потім код. **Код блоків Б–Е не писався.** Порядок виконання після погодження: Б → (Е за планом) → В, Г, Д.

Усе, що нижче названо «пропозицією», це моя пропозиція, а не ухвалене рішення. Питання, на які потрібна твоя відповідь, зібрані в кінці кожного блоку.

Папки `core/`, `content/schema`, `exercises/host` — це «ядро». Усе під `exercises/types/`, `themes/`, `content/courses/` додається файлами й не вимагає правок ядра.

### Б.3. Інтерфейси (чернетка)

```ts
// core/types.ts
export type Skill = 'metrics' | 'offers' | 'creatives' | 'landers' | 'accounts_payments' | 'analytics';
export type Difficulty = 1 | 2 | 3;

// content/schema.ts
export interface StepMeta {
  id: string;            // стабільний, однаковий в uk/en/ru (див. схему ID у content/restricted.json)
  type: string;          // ключ у реєстрі типів завдань
  skill?: Skill;
  difficulty?: Difficulty;
  draft?: boolean;       // демо-завдання й репліки, які ще перевіряє автор
  restricted?: boolean;
}
export interface Lesson { id; code; title; minutes; steps: Step[] }          // Step = StepMeta & дані типу
export interface Module { id; title; lessons: Lesson[]; checkpoint; quizzes }
export interface Course { id; name; modules: Module[]; skills: Skill[] }

// exercises/types/<тип>.tsx — єдиний контракт, який реалізує кожен тип
export interface ExerciseType<Data, Answer> {
  id: string;                                     // 'choice', 'numeric', …
  Component: React.FC<{ data: Data; resolution: Resolution | null; onAnswer(a: Answer): void }>;
  check(data: Data, answer: Answer): { correct: boolean; score?: number };   // чиста функція
  variants?(data: Data, rng: () => number): Data;  // перемішування / параметризація (блок Г.2)
  validate?(data: unknown): data is Data;          // перевірка форми даних при імпорті
}
export default exercise;                           // файл експортує реалізацію за замовчуванням

// themes/<тема>.ts
export interface ThemeDef { id: 'night' | 'day' | string; label: string; palette: Palette }

// game: механіки реагують на події, а не викликаються з екранів
export interface GameMechanic { id: string; on(event: GameEvent, ctx: GameCtx): Effect[] }
```

Автозавантаження: `core/autoload.ts` збирає `exercises/types/*`, `themes/*`, `content/courses/*/manifest.ts` через `require.context` (Expo/Metro це підтримує). Тому «новий тип/тема/курс» = новий файл у відповідній папці.

### Б.4. Теги skill / difficulty / type

- `type` уже є у кожному кроці.
- `skill` і `difficulty` зараз у контенті **відсутні**. Пропозиція: не правити `.md`, а тримати теги окремим файлом `content/tags.json` за ID кроку, із запасним правилом:
  - `skill` модуля за наявною мапою з `plan.ts` (3 і 4 → офери, 6 → креативи, 7 → ленди, 8 → аналітика, 9 → акаунти-платежі; решта за темою уроку), далі уточнюється по кроках;
  - `difficulty`: питання шару 1 → 1–2, шару 2 → 2–3; підсумкові задачі модуля → 3.
- Усі автоматично проставлені теги позначаються `draft: true` і йдуть автору на перегляд. Контент я не вигадую і не змінюю.
- Кроки модулів 01–02 (TS-файли) отримують стабільні ID за схемою `l1:q3`.

### Б.7. Тести

- **Пропозиція:** Vitest для чистої логіки (стор, `check()` кожного типу, збирання уроку, правила стріку/ліги, регулярки). Компонентні тести лише smoke-рівня. Альтернатива: `jest-expo`, важча в налаштуванні, зате ближча до RN.
- Мінімум на старті:
  - `store`: стрік (0 → 1 після уроку, лікування заморозкою, обнулення), енергія, ліга, покупки, міграція форми збереження;
  - кожен тип завдання: правильна / хибна / граничні відповіді для `check()`;
  - golden-master контенту: знімок «усі уроки: id, кількість кроків, правильні відповіді, теги» до й після міграції має збігатись.
- У CI до `tsc` додаємо `npm test`.

### Б.8. План міграції наявного контенту без втрат (фази, кожна окремим комітом, відкат = revert)

| Фаза | Що | Критерій завершення |
|---|---|---|
| 0 | Тести й golden-master: знімок усього контенту й форми збереження **до** змін | Тести зелені на поточному коді |
| 1 | `core/` (реєстр, автозавантаження) + перенос завдань у `exercises/types/*`, `ExerciseHost` замість `if` у плеєрі. Поведінка та сама | Golden-master без змін, веб-превʼю: пройти урок кожного типу |
| 2 | Розбиття `store.ts` на слайси | Форма збереження ідентична, тести стору зелені |
| 3 | Розбиття `adsmanager.ts` | `BM_SCREENS` ідентичний (довжина, порядок, `id`) |
| 4 | Теми в реєстр | Обидві теми виглядають як раніше |
| 5 | `content/schema` + курс як маніфест; теги з `tags.json` (усі `draft`) | Golden-master: контент ідентичний + нові поля |
| 6 | Скелет `grindyk/` (використовується в блоці Д) | Поведінка без змін |

Критерій блоку: тест, який додає **новий тип завдання, тему й курс лише новими файлами** (без правок у `core/`, `content/schema`, `exercises/host`) і проходить.

### Б.9. Ризики й питання до автора

1. Теги `skill/difficulty` ставляться автоматично за правилами й потребують твого перегляду (див. Б.4). Згоден?
2. Vitest чи `jest-expo` (Б.7)? Моя рекомендація: Vitest.
3. Автозавантаження через `require.context` вимагає, щоб нові файли лежали в заданих папках. Це прийнятно?
4. Обсяг: Б найбільший блок. Пропоную робити фазами 0–6 з окремим комітом і твоїм переглядом після фаз 1, 2 і 5.

## Блок Е. Веб-версія для тестерів

### Е.1. Хостинг: порівняння (ціни зі сторінок тарифів станом на жовтень 2026, перед рішенням перевір)

| Варіант | Ціна | Домен | Швидкість деплою | Нотатки |
|---|---|---|---|---|
| **Cloudflare Pages** | Free: необмежений трафік, 500 збірок/міс, 100 власних доменів на проєкт; Functions у межах ліміту Workers 100 тис. запитів/добу ([джерело](https://developers.cloudflare.com:8443/pages/platform/limits)) | Свій домен безкоштовно; DNS і TLS у Cloudflare | Хвилини; є Git-деплой і прев'ю | Додатково дає rate limiting і WAF перед сайтом (потрібно для Е.7), статика без лімітів трафіку |
| Vercel | Hobby безкоштовний, але **лише для некомерційного використання**; Pro $20 за користувача на місяць ([джерело](https://schematichq.com/blog/vercel-pricing)) | Свій домен | Дуже швидкий | Для закритого тесту продукту, що збирається монетизуватись, Hobby ризикований за умовами |
| Netlify | Free: 300 кредитів на місяць; Personal $9; Pro $20 ([джерело](https://netli.fyi/blog/netlify-pricing-and-limits)) | Свій домен із SSL на безкоштовному плані | Швидкий; прев'ю на кожен PR | Біллінг у кредитах: трафік і деплої витрачають ліміт |

**Рекомендація: Cloudflare Pages.** Безкоштовно, без ліміту трафіку, комерційне використання не заборонене, і той самий акаунт дає rate limiting (Е.7) та DNS для домену.

Веб-збірка: `expo export --platform web` (статичний експорт), публікується як статика. Збірка для тестерів робиться з `EXPO_PUBLIC_INCLUDE_RESTRICTED=false` (публічний набір контенту), якщо ти не вирішиш інакше.

### Е.2. Supabase: вхід і доступ за інвайтами

- **Google:** штатний провайдер Supabase Auth.
- **Telegram:** штатного провайдера нема; схема: Telegram Login Widget → кастомний OIDC-провайдер (`https://oauth.telegram.org`) у Supabase Auth ([джерело](https://supabase.com/docs/guides/self-hosting/self-hosted-custom-oauth-providers.md)). Це описано в документації для self-hosted; для хостингової версії треба перевірити, чи доступне налаштування кастомного OIDC на твоєму плані. Запасний шлях: Edge Function, яка перевіряє підпис Telegram і видає сесію.
- **Facebook-вхід не робимо** (рішення 4.1).
- **Інвайт-коди:** таблиця `invite_codes(code, max_uses, used_count, created_by, expires_at)` і `invite_redemptions(code, user_id, at)`. Активація через RPC-функцію `redeem_invite(code)` (`security definer`), що атомарно збільшує лічильник і відмовляє при вичерпанні ліміту. Доступ до решти даних лише для користувачів з записом у `invite_redemptions` (перевірка в RLS).
- Нових користувачів без коду реєстрація не пускає: після OAuth профіль створюється в стані «очікує код».

### Е.3. Серверний облік (RLS)

- Таблиці: `profiles`, `progress` (пройдені уроки), `answers` (відповіді з результатом), `rewards_ledger` (журнал нарахувань: монети, XP, енергія), `weekly_league` (XP за тиждень).
- **Клієнт нічого не нараховує сам.** Усі нарахування робить RPC `complete_lesson(lesson_id, answers)`: сервер перераховує правильність за еталонними відповідями й записує в журнал. Клієнт лише показує результат.
- RLS: користувач бачить і змінює лише свої рядки; прямий `insert/update` у `rewards_ledger`, `progress` заборонений (лише через RPC); рейтинг читається через view з обмеженим набором полів.
- Складність: еталонні відповіді мають жити на сервері, а не в бандлі (повʼязано з Е.5).

### Е.4. Аналітика подій

Таблиця `events(user_id, session_id, name, props jsonb, at)`. Події: `lesson_start`, `lesson_complete`, `lesson_exit` (з номером кроку), `answer` (id питання, правильно/ні, час), `session_start`, `session_end`. З цього рахуються D1/D7 (SQL-view) і помилки по кожному питанню. Запис через RPC з перевіркою користувача. Без сторонніх SDK на першому етапі.

### Е.5. Контент із сервера, помодульно

Це найважче. Зараз весь контент зашитий у бандл, тому будь-хто може його витягти з JS-файлу.

Варіанти:
1. **Повний (рекомендований як ціль):** контент лежить у БД чи в приватному бакеті Storage, модуль віддається після входу й коли попередній модуль пройдено (RLS + RPC `get_module(id)`). Відповіді перевіряються на сервері.
2. **Поетапний (рекомендований для першого тесту):**
   - Етап 1: у бандлі лишається лише Модуль 01 і структура (назви, порядок); решта модулів приходить з сервера після входу цілим модулем. Перевірка відповідей поки на клієнті.
   - Етап 2: перевірка відповідей переїжджає на сервер (`complete_lesson`).
   - Етап 3: контент шифрується або віддається частинами; водяний знак і ліміти (Е.6–Е.7).
3. Чому не все одразу: для першого тесту на кількох десятках людей повний захист коштує тижнів роботи, а ризик витоку обмежується інвайтами, водяним знаком і лімітами.

### Е.6. Водяний знак

Ледь помітний текстовий оверлей із ніком тестера (низька непрозорість, діагональний повтор) на екранах уроку й результатів. Це стримує, а не захищає від скріншота.

### Е.7. Ліміт запитів

- Cloudflare rate limiting на домен перед сайтом і на ендпоінти контенту;
- на боці Supabase: лічильник у БД всередині RPC `get_module` (наприклад, N модулів за годину на користувача, помітка підозрілих).
- Контент віддається лише авторизованим користувачам; масове викачування скриптом упирається в ліміти й у токен.

### Е.8. Що потрібно від автора

1. Розморозити проєкт Supabase (він на безкоштовному плані призупинений, див. 4.1) і вирішити, чи лишаємось на Free (50 000 MAU, 500 МБ БД, пауза після тижня неактивності) чи беремо Pro ($25 на місяць, 100 000 MAU, без паузи) ([джерело](https://supabase.com/pricing.md)). Для тестерів рекомендую Pro, бо пауза зламає тест.
2. Акаунти: Cloudflare, Google Cloud (OAuth-клієнт), Telegram-бот через @BotFather (для Login Widget).
3. Домен (рекомендація: окремий субдомен для тесту) і хто ним керує.
4. Оплата: Supabase Pro і домен. Хостинг і Cloudflare безкоштовні.
5. Рішення: етапи з Е.5 (так / одразу повний захист).
6. Список тестерів і хто видає інвайт-коди.

## Блок В. Діагностика й адаптація (після Б)

Залежить від тегів `skill/difficulty` з Б.4.

1. **Вхід:** картка «Підлаштувати курс під тебе (~3 хв)» на екрані результатів після уроку 1.1 і кнопка в Профілі. Зараз є проста версія на головній (`/adapt`), вона замінюється.
2. **Короткі питання** (прибрані з онбордингу): бюджет, час на день, стиль навчання, що лякає, дедлайн, вертикаль.
3. **Адаптивний тест:** 6 навичок; старт з `difficulty 2`; правильно → складніше, помилка → простіше; 2–3 питання на навичку, максимум 15. Питання з наявних уроків за тегами. **Залежність:** без тегів (Б.4) тест не збереш; якщо теги не погоджені, питань на складність 1 і 3 може не вистачати. Потрібен звіт покриття «навичка × складність» до коду.
4. **Результат:** рівень 0–3 на кожну навичку (за кількістю правильних на складнішому рівні).
5. **Реальний вплив:**
   - урок «можна пропустити», якщо рівень навички ≥ difficulty уроку; на вузлі міні-тест із 3 питань, ≥2 правильні → урок зараховано з 50% XP;
   - модулі за страхами й метою отримують «Фокус» і вагу ×2 у тренуваннях;
   - слабкі навички частіше (×2) у тренуваннях і повторах (SRS);
   - тривалість курсу перераховується від цілі дня.
6. **Екран результату:** «пропускаєш N уроків, економиш ~X хв, фокус: …». X береться з `minutes` пропущених уроків.
7. **Повторна діагностика** не частіше ніж раз на 14 днів (поле `diagnosedAt` у слайсі `progress`).

Питання до автора: (а) чи вважати «рівень 0–3» таким, що відповідає `difficulty 1–3` напряму (рівень 3 = може пропускати все до складності 3)? (б) Скільки XP дає зарахований міні-тестом урок: 50% від повного (як у твоїх вимогах).

## Блок Г. Нові типи завдань (після Б)

Кожен тип = один файл у `exercises/types/` (контракт з Б.3). Демо-контент: по 3 завдання на тип на теми модулів 01–02, усі `draft: true`. Наявний контент не змінюється.

| Тип | Дані | Перевірка | Генератор варіантів |
|---|---|---|---|
| `swipe-keep` «лишити / вимкнути» | картки адсетів із метриками, правильна дія на кожну | % правильних свайпів ≥ порогу | перемішування карток |
| `campaign-diagnosis` | таблиця метрик → дія (масштабувати / чекати / вимкнути) | збіг дії | перестановка рядків |
| `budget-split` | сума й адсети, повзунки | правило (формула або діапазони) | випадкова сума з кратністю |
| `truth-myth` | бліц-твердження, свайп вправо/вліво | % вірних за таймером | перемішування |
| `pick-winner` | два креативи з метриками | вибір + пояснення | міняє порядок A/B |
| `param-numeric` | шаблон із формулою й діапазонами чисел | розрахунок за формулою з допуском | нові числа при кожному показі |

**Правила збирання уроку** (`content/assemble.ts`): не більше 2 кроків одного типу поспіль; складність росте всередині уроку; 1–2 повтори з минулих уроків із SRS. Це стосується нових уроків і тренувань; наявні уроки в порядку, заданому автором, не переставляються.

**Важливо щодо контенту:** демо-завдання — це приклади форми. Правильні відповіді й формулювання для навчального змісту має перевірити автор (`draft: true` видно в інтерфейсі розробника, у публічній збірці `draft`-завдання за замовчуванням не показуються).

Питання до автора: чи показувати `draft`-завдання тестерам (за замовчуванням ні)?

## Блок Д. Гріндік v1 «живий» (після Б, без LLM)

Модуль `grindyk/`, чиста логіка + таблиці реплік. Нічого не вигадується на льоту: репліки беруться з наявних фраз (`phrases.ts`), порожнє позначається `TODO` для автора.

1. **Темперамент:** `coach | joker | mentor | support | veteran-cynic`; випадковий при старті; змінюється в Налаштуваннях. Зберігається в слайсі `player`.
2. **Настрій:** обчислюється з подій (стрік, серія помилок, відсутність, рекорд): `energetic | calm | tired | proud | worried`.
3. **Розпорядок за місцевим часом:** ранок, день, пік 16–20, вечір, ніч, вихідні → своя поза й набір реплік. Основа вже є в `greetingKind()`.
4. **Пам'ять про гравця:** мета, дата старту, часті помилки (за термінами), рекорди, дні відсутності → шаблони з підстановками `{name}`, `{goal}`, `{term}`, `{days}`.
5. **Ініціатива:** не більше 1 разу за сесію на головній: питання, виклик або епізод «зі свого дня».
6. **Рівень стосунків 0–4:** від днів активності й точності; відкриває теми й тон.
7. **Фонова анімація:** якщо гравець 5 с нічого не робить на головній, змінюються пози з наявних (з правилом «не повторювати попередню»).
8. **Структура реплік:** `тригер × темперамент × рівень стосунків`. Заповнюємо наявними фразами; порожні клітинки `TODO`; не більше 2 прикладів на клітинку; усі нові `draft: true`.

Потрібна відповідь автора: (а) закритий список тригерів для таблиці реплік (я запропоную з наявних `PhraseKind`, ~40 штук) чи твій; (б) як мапити наявні фрази на темпераменти: перший прохід я зроблю за тоном, ти перевіриш.
