## 1. Готовність до Vercel (без акаунта й без деплою)

Що зроблю:
- `app-mvp/vercel.json`:
  - `buildCommand`: `npx expo export --platform web`
  - `outputDirectory`: `dist`
  - `rewrites`: усі шляхи на `/index.html` (щоб працювали адреси на кшталт `/lesson/l1`, експорт у режимі одного файла)
  - `headers`: `X-Robots-Tag: noindex, nofollow` (пошуковики не індексують); поруч `public/robots.txt` з `Disallow: /`.
- Перевірю локально: `npx expo export --platform web` без помилок, `dist` відкривається простим локальним сервером і маршрути працюють при прямому відкритті.
- `docs/DEPLOY_VERCEL.md`: точні значення для форми Vercel простою мовою (Root Directory = `app-mvp`, Framework Preset = Other, Build Command, Output Directory, версія Node) і перелік env-змінних.

Env-змінні, які ти вписуватимеш у Vercel (усі публічні за задумом; секретів у Vercel нема):

| Змінна | Що це |
|---|---|
| `EXPO_PUBLIC_SUPABASE_URL` | адреса проєкту Supabase |
| `EXPO_PUBLIC_SUPABASE_ANON_KEY` | публічний ключ Supabase (доступ обмежують правила RLS, не ключ) |
| `EXPO_PUBLIC_TELEGRAM_BOT` | імʼя бота без @ (для кнопки входу) |
| `EXPO_PUBLIC_INCLUDE_RESTRICTED` | `false` = публічний набір контенту без ризикових фрагментів (див. питання 3) |

Секрети (`TELEGRAM_BOT_TOKEN`, `SERVICE_ROLE`) **не йдуть у Vercel**: їх вписують у Supabase як секрети функції входу (див. розділ 2).

## 2. Закритий доступ: Telegram + білий список

### 2.1 Як це працює

1. На сторінці входу кнопка «Увійти через Telegram» (офіційний Login Widget).
2. Telegram віддає застосунку підписані дані (id, імʼя, @username, час, `hash`).
3. Застосунок відправляє їх у **функцію Supabase `telegram-auth`**. Вона:
   - перевіряє підпис Telegram токеном бота (це можна лише на сервері; тому токен лежить у секретах Supabase);
   - перевіряє, що вхід свіжий (до 5 хвилин);
   - шукає @username у `allowed_users`; якщо нема або статус `blocked`, повертає відмову, застосунок показує екран «Доступ лише для запрошених»;
   - при першому вході привʼязує числовий Telegram-id до запису (див. питання 1);
   - створює або знаходить користувача Supabase, видає нову сесію.
4. Далі застосунок працює як звичайний залогінений користувач.

Це не готова «кнопка Supabase»: Telegram у Supabase підтримується лише через власний провайдер/функцію, тому я пишу функцію входу сам (приблизно 100 рядків) і окремий екран входу.

### 2.2 Таблиці й правила (все одним SQL-файлом, який ти вставиш у Supabase)

`app-mvp/supabase/migrations/0001_closed_test.sql`:

| Таблиця | Для чого | Хто бачить |
|---|---|---|
| `allowed_users` (username, імʼя, статус `invited/active/blocked`, telegram_id, is_admin, активний сеанс) | білий список | лише адмін; решта нічого |
| `progress` (user_id, state JSON, оновлено) | прогрес гравця з телефона на телефон | користувач бачить лише свій рядок |
| `feedback` | відгуки | користувач додає, читає лише адмін |
| `events` | аналітика | користувач додає, читає лише адмін |

Правила (RLS): усе, крім входу, доступне лише користувачеві, чий запис у `allowed_users` активний **і** чий поточний сеанс збігається з активним. Для цього одна функція `is_active_user()`, на неї посилаються всі політики.

### 2.3 Один активний сеанс на акаунт

- При кожному вході функція `telegram-auth` генерує новий `session id`, кладе його в `allowed_users.active_sid`, робить глобальний вихід (скасовує старі токени оновлення) і повертає новий `sid` застосунку.
- Застосунок надсилає `sid` у заголовку кожного запиту; правило RLS порівнює його з `active_sid`. Старий пристрій одразу отримує відмову, показує «Вхід виконано з іншого пристрою» і розлогінюється. Заголовок потрібен, бо без нього старий пристрій міг би тихо оновити токен і лишитись у системі.

### 2.4 Прогрес гравця

Зараз прогрес живе лише на пристрої (локальне сховище). Для тесту пропоную **синхронізувати весь стан гравця одним JSON** у `progress`: вхід з іншого пристрою підтягує прогрес, застосунок зберігає зміни з затримкою кілька секунд. Нарахування коїнів і XP лишаються на клієнті (для закритого тесту без оплат це припустимо; серверний облік із блоку Е лишається на потім). Конфлікти: перемагає новіший `updated_at`.

### 2.5 Адмінка для тебе

Окремий екран `/admin` у застосунку, видимий лише записам з `is_admin`: список тестерів (додати/заблокувати @username) і список відгуків. Альтернатива без коду: таблиці в панелі Supabase (Table Editor). Пропоную обидва: адмінку для відгуків і тестерів, Supabase для дрібних правок.

## 3. Захист контенту

- **Водяний знак:** ледь помітний повтор «@нік» діагоналлю на екранах уроку й результатів (прозорість близько 6–8%, не ловить дотики).
- **Контент у бандлі.** Для ~20 знайомих баєрів **лишаю уроки в бандлі**, винесення на сервер позначаю як **фазу 2**. Обґрунтування: перенесення вимагає серверної перевірки відповідей і завантаження модулів, це тижні роботи й сама по собі велика міграція; для 20 людей з білим списком, водяним знаком і неіндексованим посиланням ризик допустимий. **Ризик, який треба знати:** сам файл застосунку (JS-бандл) на Vercel віддається будь-кому, хто знає адресу, навіть без входу. Вхід закриває дані й функції, але не приховує тексти уроків від людини, яка вміє відкрити код сторінки. Запишу це в `DECISIONS.md` як відомий ризик.
- Зменшити ризик без коду можна так: `EXPO_PUBLIC_INCLUDE_RESTRICTED=false` (ризикових матеріалів у бандлі просто нема, див. пакет 2, блок А) і не поширювати посилання поза списком.

## 5. Міні-аналітика

Події в таблицю `events`: `lesson_start`, `lesson_complete` (з точністю), `lesson_exit` (з номером кроку, на якому вийшли), `session_start`. Невеликими пакетами раз на кілька секунд і при згортанні вкладки; без сторонніх сервісів. У `/admin` проста зведена таблиця: скільки тестерів заходило, скільки уроків почато й закінчено, де найчастіше виходять.

## 6. Як перевіряти без твоїх акаунтів

Справжній вхід я перевірити не зможу: нема твого бота й розмороженого Supabase. Тому:
- чисту логіку (перевірка підпису Telegram, правила «хто допущений», один сеанс) покриваю автотестами;
- додаю режим `EXPO_PUBLIC_CLOUD=mock` (локальна «імітація сервера»): у ньому видно екран входу, екран «лише для запрошених», відгуки, водяний знак, подію аналітики. Цим перевіряю інтерфейс у превʼю 360×640 і 390×844;
- ця імітація **вимкнена** у збірці для Vercel (там режим реального Supabase).
- Перший реальний наскрізний тест: ти зробив бот і розморозив Supabase, я підключаю й проходимо вхід разом.

## 8. Питання до тебе (потрібна відповідь до початку 3.2)

1. **Білий список за @username.** У Telegram @username можна змінити або віддати іншій людині. Пропоную: ти додаєш @username, а при першому вході система привʼязує ще й числовий id; далі впізнає за id. Тоді чужий не зайде, навіть якщо захопить звільнений @username. Згоден? (Якщо в баєра нема @username у Telegram, він зайти не зможе, нехай поставить його.)
2. **Прогрес на сервері.** Синхронізація одним JSON (2.4), нарахування лишаються на клієнті. Підходить для тесту?
3. **Ризикові матеріали в тестовій збірці.** Тестери це баєри. Рекомендую `EXPO_PUBLIC_INCLUDE_RESTRICTED=false` (публічний набір). Якщо їм потрібен повний курс, поставимо `true`, але тоді ці тексти будуть у файлі, який отримує кожен, хто знає адресу.
4. **Vercel Hobby.** Безкоштовний тариф Vercel за умовами призначений для особистого некомерційного використання. Закритий тест майбутнього комерційного продукту межує з цим; найпростіше безпечне рішення: тариф Pro (близько $20 на місяць за користувача, за відкритими даними цін станом на жовтень 2026, звір на сторінці тарифів). Рішення за тобою.
5. **Адмінка в застосунку (`/admin`)** плюс Supabase для дрібниць: згоден, чи лише Supabase Table Editor?
6. **Supabase Free чи Pro.** На Free проєкт засинає після тижня без активності (так уже сталося), це зламає тест. Для тесту рекомендую Pro ($25 на місяць) або хоча б заходити в проєкт щотижня.
