# Вхід за одноразовим кодом від бота замість Telegram-віджета: план на погодження

Статус на 2026-10-18: **план, код не писався.** Заміна кроку 3.2 пакета 3; решта 3.2 (білий список, привʼязка до числового telegram-id, один активний сеанс, прогрес, закриті маршрути) лишається без змін.

## 1. Потік, який пропоную (з одним уточненням до твого опису)

Твій потік: «Увійти» → «напиши боту /start» → бот присилає 6-значний код → вводиш код у застосунку. Є одна проблема: застосунок не знає, чий це код, бо людина вводить лише цифри. Якби код шукали **лише за цифрами**, то злочинцю не треба знати нічийого імені: достатньо вгадати будь-який дійсний код серед активних (з 20 тестерами це 1 шанс на ~50 тис. спроб; рейт-ліміт це гальмує, але не усуває). Тому пропоную стандартний прийом: **посилання з одноразовою міткою**.

1. Натискаєш у застосунку «Увійти». Застосунок створює випадкову **мітку** (nonce, 24 символи, лишається лише на цьому пристрої).
2. Екран: «Відкрий бота й натисни Start» (кнопка відкриває `t.me/<бот>?start=<мітка>`) і поле для 6-значного коду. Таймер 5:00.
3. Telegram показує боту повідомлення `/start <мітка>`. Бот (webhook на Supabase) бачить **telegram-id** і @username відправника, перевіряє білий список і надсилає: «Код входу: 123456. Дійсний 5 хвилин. Нікому його не передавай».
4. Вводиш код у застосунку. Застосунок шле на сервер `{мітка, код}`.
5. Функція `verify-code` знаходить запис за міткою, перевіряє код, строк і кількість спроб, **ще раз** звіряє білий список за telegram-id (привʼязка id при першому вході за @username, як і було), видає сесію й новий активний сеанс (як у поточному `telegram-auth`).

Що це дає порівняно з «лише код»: код діє **тільки з міткою, яку знає пристрій, що почав вхід**. Вгадувати нема чого: потрібні і мітка, і код, і Telegram-акаунт зі списку.

Якщо людина просто відкриє бота вручну й напише `/start` (без мітки), бот відповість: «Натисни «Увійти» в застосунку: він відкриє мене з кнопкою Start» і код **не** надішле. Це свідомо суворіше за твій опис; якщо хочеш, щоб працював і ручний `/start`, скажи: тоді код шукатиметься за цифрами (слабший захист, див. вище).

## 2. Де webhook і як усе влаштовано

| Частина | Де живе | Навіщо |
|---|---|---|
| `telegram-webhook` | Edge Function Supabase (**Verify JWT вимкнено**: Telegram не вміє слати JWT) | приймає повідомлення боту, генерує код, надсилає через Bot API `sendMessage` |
| `verify-code` | Edge Function Supabase (**Verify JWT вимкнено**: виклик до входу) | перевіряє `{мітка, код}`, видає сесію. **Замінює `telegram-auth`** |
| Захист webhook | `secret_token` при `setWebhook`; Telegram додає заголовок `X-Telegram-Bot-Api-Secret-Token`, функція відкидає запити без правильного значення | сторонні не можуть підробити «повідомлення від Telegram» |
| Рейт-ліміт | таблиця `login_throttle` | ≤ 20 спроб введення коду з однієї адреси за 10 хв; ≤ 1 код на 30 с і ≤ 5 кодів на годину на один telegram-id (щоб бот не став спам-машиною) |

Решта функцій (білий список, сеанс, `session_me`, `save_progress` тощо) не змінюється.

## 3. Секрети

У Supabase → Edge Functions → Secrets (одні й ті самі для обох функцій):

| Секрет | Що це | Хто створює |
|---|---|---|
| `TELEGRAM_BOT_TOKEN` | токен від @BotFather (вже був) | автор |
| `TELEGRAM_WEBHOOK_SECRET` | випадковий рядок для webhook (до 256 символів: літери, цифри, `_`, `-`; придумує автор, приблизно 32 символи) | автор |

Ключ для хешування кодів я виводжу з токена бота, тож **окремого третього секрету нема**. `SUPABASE_URL` і `SUPABASE_SERVICE_ROLE_KEY` Supabase підставляє сам. У Vercel нічого нового не вписується (для застосунку потрібне лише імʼя бота, `EXPO_PUBLIC_TELEGRAM_BOT`, воно вже є).

Реєстрація webhook (один раз, автор, у браузері): адреса виду
`https://api.telegram.org/bot<ТОКЕН>/setWebhook?url=https://<ПРОЄКТ>.supabase.co/functions/v1/telegram-webhook&secret_token=<СЕКРЕТ>&allowed_updates=["message"]&drop_pending_updates=true`
Відповідь має бути `{"ok":true,...}`. Увага: токен потрапляє в історію браузера; після цього історію можна почистити. Покрокову інструкцію й готові підстановки допишу в `DEPLOY_VERCEL.md`.

## 4. Зміни в базі (міграція `0002_login_codes.sql`, поверх 0001)

```
login_codes   (id, nonce_hash, telegram_id, tg_username, first_name,
               code_hash, expires_at, attempts, used_at, created_at)
login_throttle(key, window_start, count)
```
- `nonce_hash` і `code_hash` це HMAC-хеші; самих мітки й коду в базі нема, лише в повідомленні користувачу.
- Нова `/start` з тією ж міткою замінює попередній код цієї мітки (одна активна пара).
- `expires_at` = створення + 5 хв; `attempts` ≤ 5, після цього код мертвий (потрібне нове `/start`); `used_at` робить код одноразовим.
- Обидві таблиці з увімкненим RLS **без політик**: доступні лише функціям із `service_role`; `anon` і `authenticated` не мають жодних прав.
- Старі записи (старші за добу) функції прибирають самі при кожному виклику.
- `telegram_id` у `login_codes` поки лише для звʼязку «код → людина»; рішення «пускати чи ні» й привʼязка id до `allowed_users` лишаються у `verify-code` (як зараз).

## 5. Зміни в застосунку

- Екран входу: крок 1 кнопка «Увійти через Telegram», крок 2 інструкція + кнопка «Відкрити бота» + поле коду (6 цифр, цифрова клавіатура) + таймер + «Не прийшов код? Натисни Start ще раз». Помилки простою мовою: невірний код (лишилось N спроб), код прострочено, забагато спроб, «Доступ лише для запрошених», «Бот не відповів: перевір, що натиснув Start».
- Режим-імітація (`EXPO_PUBLIC_CLOUD=mock`): замість віджета панель «Telegram-бот (імітація)»: вибір тестового акаунта, кнопка «Надіслати /start боту», і «повідомлення від бота» з кодом на екрані. Без реального Telegram можна пройти весь потік.
- Спільна логіка (генерація мітки й коду, хешування, перевірка коду/строку/спроб, ліміти) у `src/cloud/shared/`, одна для імітації, Edge Functions і автотестів. Обробники `/start` і перевірки коду я пишу як чисті функції з «впровадженими» залежностями (база, відправка повідомлення, годинник): це дозволяє автотестами пройти увесь потік (прострочення, 5 спроб, повторне використання, ліміти) без Telegram і Supabase.
- Telegram-віджет і функція `telegram-auth`: **пропоную прибрати** (видалити компонент віджета, `telegram-auth`, `checkTelegramPayload` разом з тестами; в історії git вони лишаються). Запасний варіант за прапором збільшує код і поверхню атаки заради способу, який ти вже вважаєш ненадійним. Якщо хочеш лишити, скажи: зроблю прапор `EXPO_PUBLIC_LOGIN_METHOD=widget|code` (за замовчуванням `code`).

## 6. Що змінюється для тебе (спрощення)

- **Домен більше не потрібен для входу.** Раніше бот привʼязувався до адреси сайту командою `/setdomain`, тому для перевірки входу був потрібен пробний деплой на Vercel. З кодом від бота `/setdomain` не потрібен, і вхід можна перевірити навіть локально й до Vercel. Деплой на Vercel тепер потрібен лише для самого тесту.
- Пункт `/setdomain` прибираю з розділу 3 і чеклиста `DEPLOY_VERCEL.md`; додаю пункти «секрет вебхука», «деплой двох функцій», «реєстрація webhook».

## 7. Ризики й обмеження

1. **Фішинг коду.** Хтось може надіслати баєру своє посилання з чужою міткою й попросити «перешли код»; код тоді впустить зловмисника в акаунт жертви. Захист тільки текстовий (у повідомленні бота «Нікому не передавай код»); технічно це неможливо виключити в потоці «код у чат».
2. **Затримки Telegram.** Повідомлення від бота зазвичай приходять за секунди, але інколи повільніше; строк 5 хв це враховує.
3. **Один webhook на бота.** Якщо потім захочеш використовувати цього ж бота для іншого, webhook буде зайнятий (для цього бота використаємо окремий).
4. **IP-ліміт.** Адреса береться із заголовка запиту; за NAT (один офіс) люди ділять ліміт 20 спроб на 10 хв: достатньо для ~20 баєрів.
5. **Не перевірено на справжньому Supabase й Telegram.** Це відомо заздалегідь: логіку покрию автотестами й імітацією, наскрізний тест із твоїм ботом пройдемо разом (як і було).
6. **Free-ліміти Supabase:** кожен вхід це 2–3 виклики функцій; для 20 тестерів це мізер.
