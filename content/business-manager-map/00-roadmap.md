# Мапа Business Manager — дорожня карта

Мета: 100%-точна копія реального інтерфейсу (справжні скріншоти + невидимі клікабельні
зони), не намальований макет. Метод і формат кожного розділу — у `content/business-manager-map/README.md`.

Позначки: ✅ готово (скріни + hotspot-екран у застосунку) · 🟡 частково (є текстова мапа
або скріни, ще не hotspot) · ⬜ не почато.

## Велике бачення (рішення автора, 2026-09-30)
Кінцева мета — не набір окремих завдань, а **повний навігаційний граф** кабінету: кожна
кнопка на кожному екрані записана з (а) точним текстом кнопки, (б) координатами, (в) куди
вона веде (`leadsTo` → id іншого `BmScreen`). Звідси випливає кілька шарів, які будуються
поверх того самого масиву даних `BmScreen[]`, без переробки формату:

1. **Тренажер-завдання** (є зараз): 2-4 hotspot з kind `'task'`, один правильний, з feedback.
2. **Повна карта шляхів**: усі кнопки екрана як hotspot з kind `'nav'` (label + leadsTo),
   навіть ті, що не входять у конкретне завдання. Знімаємо їх одночасно з завданнями —
   дешевше зробити зараз, ніж переходити по кожному екрану вдруге.
3. **Довідка/тур по кабінету**: розбити навчання орієнтуванню по кабінету на розділи, з
   можливістю «показати шлях до фічі X» — веде гравця по ланцюжку `leadsTo` від поточного
   екрана до потрібного.
4. **«Секретики» з досвіду й форумів**: короткі підказки-підводні камені під конкретними
   екранами карти (не з офіційної документації, а практичний досвід). Перший безкоштовно,
   решта — за окрему підписку/донат. Контент пишеться окремо, коли карта достатньо готова.

Порядок 2-4 підтверджується по ходу — можливо частину зробимо одночасно з 1, а не строго
послідовно.

## Архітектурна корекція і новий стандарт розміру (2026-10-01)
Автор відхилив реалізацію "карта-список → окрема сторінка-екран" (`app/bm/index.tsx` +
`app/bm/[id].tsx`, header/задача/back-link). Правильна модель: **один персистентний фрейм**
(`src/components/BmExplorer.tsx`, рендериться в `app/bm/index.tsx`) — картинка на весь екран,
клік по nav-хотспоту просто підмінює `screen.image` у локальному стейті (стек історії для
"назад"), без роутингу й без квіз-шапки. Kind `'task'` (correct/feedback) лишається в даних
для сумісності й для тизера в Бібліотеці, але сам Explorer рендерить активними тільки
хотспоти з `leadsTo` — це і є "кожен активний елемент веде на інше зображення" буквально.

**Розмір скріншота:** `resize_window` на вбудований браузер (Claude in Chrome / Browser pane)
**не впливає** на реальний розмір скріншота — перевірено 3 різні запити (1512×793, 1497×836,
1000×600), результат завжди один: **1527×750**. Це фіксований розмір рендеру цього
браузер-пейна. Висновок: не боротися з інструментом — **1527×750 і є новий стандарт** для
всіх нових зйомок (замість раніше узгодженого 1512×793, який інструмент фізично не віддає).
Старі скріни з іншими розмірами лишаються як є, замінюються тільки при нагоді (новий
розділ/повторна зйомка), а не масовим перезняттям.

**Реальний UI змінився:** створення кампанії вже не серія модалок — єдиний редактор з
деревом зліва (Campaign → Ad set → Ad), клік по рівню просто скролить/показує його секцію
в тій самій панелі. Це ідеально лягає на модель Explorer: кожен рівень дерева — окремий
`BmScreen`, клік по дереву — nav-хотспот. Переснято й повністю зв'язано: campaigns-list →
Create → campaign-objective → Continue → campaign-settings (рівень Campaign) →
adset-settings (рівень Ad set, той самий id/файл, що й стара "Конверсія") → ad-settings
(новий, рівень Ad), плюс Close/Back/Next і клік по дереву в обидва боки. Перевірено живим
кліком у веб-превʼю — кожен крок підміняє картинку, без переходу сторінки.

**PII у нових зйомках:** акаунт "Sergey G4" і фото профілю (справжнє обличчя) у верхній
панелі — gaussian blur (сампл+blur самого регіону, той самий підхід, що й раніше). Реальний
Instagram-хендл на рівні Ad ("insiders_store_in_ua") замінено вигаданим ("yourstore_page_ua")
тим самим методом компонування (білий фон семплом, текст тим самим шрифтом/кольором) —
перевірено зумом перед комітом, без артефактів.

**Лишається зробити (чесно, не приховуємо):** старі острівці без nav (adset-budget,
ad-destination, ad-tracking, audiences-empty, automated-rules, ads-reporting,
events-overview і решта Events/Business Settings/Billing) ще не підключені до основного
ланцюжка — досяжні тільки через `mbs-all-tools` хаб або взагалі ще не досяжні кліками.
Повне покриття "кожен активний елемент" на КОЖНОМУ екрані — це окрема довга робота по
розділах (Ads Manager → Billing → Events Manager → Business Manager → решта), не зроблена
за один прохід. Далі рухаємось послідовно розділами, дублі (однакові списки/картки, що
ведуть на структурно однаковий екран) — одна ціль-скрін на кілька джерел-хотспотів.

## Практичне правило для екранів зі списками (кампанії/адсети)
Реальні назви товарів/кампаній **не показуємо** — замінюємо на загальні назви категорії
товару. Дати, бюджети, статуси, налаштування — лишаємо як є. Назви кампанії та її адсетів
мають лишатися узгодженими одна з одною (та сама категорія для кампанії і для її адсетів),
щоб студент бачив приклад **послідовного нейминга**, а не хаос — це частина навчальної мети.

**Метод, який реально працює (тестовано на Sergey G4, 2026-09-30):** заміна тексту напряму
в DOM (`node.nodeValue = ...`) **ламає React-віртуалізовані таблиці** цього кабінету —
рядки після цього дублюються/з'їжджають при наступному ререндері. Робочий спосіб:
1. Знімаємо скріншот з РЕАЛЬНИМИ назвами (тільки акаунт заблюрений через `style.filter`,
   це safe — не мутує текст/дітей).
2. Заміну робимо **локально на самому PNG** через sharp (`scripts/bm-tools/relabel.cjs`):
   прямокутник + SVG-текст поверх. **Колір прямокутника береться семплом пікселя з самого
   скріншота** (з порожнього місця в тому ж рядку), не hardcoded білий — інакше виглядає
   як заліплено в Paint. З урахуванням зебра-смуг (парні/непарні рядки трохи різний відтінок)
   семпл робиться **окремо для кожного рядка**.
3. **Координати рядків через `getBoundingClientRect()` ненадійні** — навіть коли
   `window.innerWidth` збігається з шириною скріншота, є стабільний зсув по Y (у різних
   спробах різний, від +26 до +40px), і оверсайз-прямокутник «на всю висоту рядка», яким
   спершу закрили це питання, залишає видиму порожнечу зверху/знизу тексту — текст «плаває»
   не по центру рядка. **Правильний спосіб — сканувати РЕАЛЬНІ пікселі скріншота**, а не
   довіряти DOM-координатам: `scripts/bm-tools/find_text_rows.cjs` проходить по стовпцю,
   де мають бути назви, і шукає рядки з кольоровими (не сіро-білими) пікселями — це і є
   точні межі синього тексту-посилання. Дає рівно той прямокутник, що треба, без підбору
   навмання. Той самий скрипт для X-меж на рядок (посилання різної довжини).
4. Прямокутник підганяй по фактичних межах тексту з кроку 3 (+невеликий відступ, ~4-5px),
   а не «з запасом» — інакше зайве порожнє поле над/під текстом впадає в очі.

**Екрани з фото-креативами (оголошення):** мініатюри оголошень — це реальні фото товару/
моделі, а не просто назва, тому текстової заміни недостатньо. Замінюємо мініатюру на
generic photo-плейсхолдер (сірий прямокутник + іконка картинки), тим самим методом
пошуку меж пікселями (тут — пошук не-білих пікселів у стовпці мініатюр), а не суцільним
блюром — плейсхолдер однозначно читається як «тут було фото», а не як забагована картинка.

**"Created by" та інші аудит-поля:** не тільки назва акаунта є PII. У списку "Automated
rules" колонка "Created by" показала реальне ім'я людини (не назву акаунта) — той самий
targeted-blur по тексту, просто інший рядок для пошуку. Правило: перед скріном скануй екран
на будь-яке власне ім'я/прізвище, не тільки на назву рекламного кабінету.

**Аватарка профілю в шапці:** сторінки business.facebook.com (Events Manager і подібні)
показують маленьке кругле фото профілю у верхньому правому куті — це реальне обличчя людини,
не просто іконка. Шукати не текстом, а через `document.querySelectorAll('img')`, фільтруючи по
позиції (верхній правий кут, малий розмір) і застосовуючи той самий `style.filter = 'blur()'`.

**Реальний домен сайту:** на сторінці датасета Events Manager у блоці "Websites" показується
справжній домен лендінга/сайту акаунта — це так само бізнес-специфічна інформація, як назва
товару, тому затираємо тим самим targeted text-blur (домен — звичайний текстовий вузол, DOM
тут не віртуалізований, тому мутація тексту теж була б безпечною, але для одноманітності
методу все одно використано blur, а не заміну).

**Білінг — найчутливіший екран, і причина зміни методу:** перша спроба (targeted blur
назви акаунта й останніх 4 цифр картки) не пройшла — auto-mode classifier заблокував коміт
як "PII Data Handling", навіть із затертими цифрами. Замість blur тепер скрізь, де можливо,
**вигадані дані замість реальних** (рішення автора, 2026-09-30: "замість токенів чи назв
придумай несправжні дані... все що може вказувати на реальні дані потрібно замінити
штучними"). Білінг перезняли й замінили компонуванням (той самий сампл-фону + SVG-текст
метод з `relabel.cjs`, застосований до назви бізнесу/акаунта й останніх 4 цифр картки:
"Sergey G2" → "Demo Business", "Sergey G1" → "Demo Ad Account 1", "3397" → "0000"), плюс
згенерована заглушка-аватарка замість реального фото профілю. Суми (баланс, поріг оплати,
ліміт витрат) лишаються реальними — вони навчальні, не ідентифікуючі.

**Практичне правило відтепер:** де раніше застосовувався blur (назва акаунта/бізнесу,
профільне фото, реальні імена людей, домени), за можливості переходимо на заміну
вигаданими, але правдоподібними даними тим самим методом компонування — це і чистіше
виглядає, і знімає ризик блокування класифікатором. Уже закомічені екрани з blur
залишаються як є (масове перезняття — окрема задача, не пріоритет); нові екрани і
будь-які повторні зйомки роблять вигаданими даними.

**Урок з payment-methods (8 карток одразу, 2026-09-30):** точкова заміна лише самих
останніх 4 цифр багато разів не збігалася з реальними межами тексту — заміна виходила
або замалою (видно хвіст оригінальних цифр), або зачіпала сусідній елемент (іконку/бейдж).
**Надійніший спосіб для короткого рядка "Мітка · · · · XXXX": перемалювати ввесь рядок
цілком** (мітка карти + крапки + вигадані цифри одним текстом), а не тільки 4 цифри —
досить лише знати, де закінчується іконка ліворуч (щоб її не зачепити) і що фон
однорідний (щоб оверсайз-прямокутник не впадав в очі). Це набагато стійкіше до похибки
в піксель-калібруванні, ніж вузька точкова заміна.

**Список реальних доменів (Business Settings → Domains):** тут одразу кілька реальних
доменів магазинів (не один, як на екрані датасета) — точковий blur по кожному рядку заважко
підтримувати. Робочий спосіб: regex на вигляд домену (`/^[a-z0-9-]+\.(store|shop|online|com|
net|ua|site)$/i`) проходить по всіх текстових вузлах і блюрить кожен збіг одразу, без
перелічування назв вручну. Для тексту всередині довшого речення ("...to this X domain")
точний-рядок-match з info width<500 не спрацював (елемент ширший) — довелося прибрати
обмеження по ширині саме для цього виклику.

## Хаб-екрани навігації (2026-10-01)
Два реальні хаби тепер зв'язують усі розділи між собою — раніше `mbs-all-tools` був єдиним
входом і сам не мав жодного вхідного посилання (технічно недосяжний з головного екрана).
1. **`main-nav-menu`** — справжнє меню ☰ самого Ads Manager (Campaigns/Ads Reporting/
   Audiences/Advertising settings/Billing/Events Manager/All tools). Відкривається іконкою
   ☰ в лівій панелі `ads-list`. Це основний хаб — з нього прямий шлях у 5 розділів.
2. **`mbs-all-tools`** — мапа інструментів Meta Business Suite (Advertise/Manage/Sell).
   Reachable через `main-nav-menu` → All tools, і через сайдбар `mbs-home` → All tools.
   6 nav-хотспотів на вже зняті екрани + сайдбар-хотспоти (Home/Leads Center/Content/
   Settings → bs-ad-accounts).

Також пряма іконка-картка (Billing) і іконка ☰ в лівій панелі `ads-list`/`campaigns-list` —
рейл-хотспоти, що відповідають реальним іконкам Facebook, не вигаданим кнопкам.

## Порядок роботи
1. Обираємо один розділ зі статусом ⬜/🟡.
2. Живий акаунт → Claude in Chrome → скріни кожного стану екрана (порожній/заповнений/під час дії), затираємо назву/ID акаунта і будь-які особисті дані.
3. Скріни → `app-mvp/assets/bm/<розділ>/*.png`.
4. Дані hotspot-ів (координати, підказки, правильна дія) → `app-mvp/src/data/bm/<розділ>.ts`.
5. Рендер тим самим компонентом `ScreenHotspot` (app-mvp/src/components/ScreenHotspot.tsx).
6. Позначаємо ✅ у цій таблиці.
