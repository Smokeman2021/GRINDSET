## Контрольна точка 1 · скидання з епохою (ТЗ 005 повністю)

**Як зроблено** (у межах 005, з поправкою на поточну гілку):
- **Епоха** — `allowed_users.progress_epoch`. Вона переживає видалення прогресу. `load_progress_v2` повертає епоху.
- **`save_progress_v2(…, p_epoch)`** читає епоху під спільним блокуванням рядка учётки (`for share`). Не та епоха → `epoch_mismatch`, нічого не записано. Операції з власною епохою (перенесення `legacy-init` / `legacy:<учётка>:<урок>`) з чужою епохою → `rejected_epoch`.
- **Параметр `p_epoch`** додано вже в 0007 (на продакшні ще не застосована, параметр там ігнорується). Так b28 може писати між кроками «v2» і «0009» вікна. 0007 видаляє стару тріаргументну версію.
- **Стара збірка.** У v2 вона нічого не пише (як і раніше). Для учёток, які вже скидались (епоха > 0), стара `save_progress` не пише **в жодному режимі**, і після відкату в legacy теж. `load_progress` після скидання повертає порожнє.
  - Наслідок: якщо після скидання відкотитись на b24 + legacy, прогрес скинутих учёток у b24 не зберігається до повернення в v2. Інакше стара збірка повернула б видалене зі свого пристрою. Записано в план відкату.
- **`reset_progress(p_run_id, p_account_ids)`:**
  - лише власник: SQL Editor або `service_role`; права `public` / `anon` / `authenticated` відкликано явно;
  - лише режим v2;
  - явний непорожній список; варіанта «усі» немає;
  - повтор з тим самим ідентифікатором → той самий результат, нічого не змінює;
  - для кожної учётки: прогрес і журнал → `progress_archive` → видалення → епоха + 1;
  - результат по кожній учётці: заархівовано / видалено.
- **`restore_progress(p_run_id, p_account_id)`:**
  - повертає рядок і журнал з архіву з новою епохою;
  - поточний прогрес після скидання — в архів `<run>:before-restore`;
  - повторне відновлення → той самий результат.
- **Клієнт** (`progressSync`):
  - епоха зберігається в метаданих синхронізації кожної учётки, поруч із чергою;
  - на старті інша епоха → очищення локального стану, черги й відкладених операцій **лише цієї учётки** (з онбордингом і вибором персонажа), потім серверний стан; перенесення старих даних не виконується;
  - `epoch_mismatch` під час відправки → те саме очищення й повторне завантаження.
